# 文档冲突检测

上传文件解析、向量化及 ES 写入成功并回写用量后发布 Spring 应用事件；单文件重建索引也发布事件。监听器在事务提交后将任务交给独立有界线程池，扫描失败不影响入库。

管理员在知识库的“文档冲突”按钮中查看、分页筛选和处理记录。

- `KEEP_NEW`：删除已有的整篇文档。
- `KEEP_EXISTING`：删除新的整篇文档。
- `IGNORED`：保留双方，标记不是冲突。
- 删除文档后，它参与的其他待处理记录标记为 `OBSOLETE`。

接口仅限 ADMIN：

- `GET /api/v1/admin/document-conflicts?status=PENDING&page=1&size=20`
- `POST /api/v1/admin/document-conflicts/{id}/resolve`，JSON：`{"action":"IGNORED","note":"不同环境"}`。

配置在 `knowledge.conflict`：默认启用检测，余弦阈值 0.9、字符二元组 Dice 阈值 0.8；每文件扫描前 200 块，每块取 3 个邻居，最多记录 50 个候选。刷新 ES 后加载新分块，兼容现有随机文档 ID；排除自身文件，限定同上传者、公开或同组织标签，且不比较不同模型版本。

规则提取日期、版本、数字，比较屏蔽后的句子骨架及关键值集合；这不是完整的语义矛盾判断，可能漏掉纯文字否定、单位换算、数字位置互换等情况。LLM 确认默认关闭，通过 `KNOWLEDGE_CONFLICT_LLM_CONFIRM_ENABLED=true` 开启；每批最多 8 对，模型失败或遗漏候选时保留规则结果。

JPA 根据实体创建 `document_conflicts` 表（项目默认 `ddl-auto=update`）；生产禁用自动 DDL 时需预先应用对应表结构。分块对唯一索引阻止重复记录。

这是尽力执行的本地后台任务，没有持久化队列、宕机恢复和自动重试；多实例不会广播事件。数据库唯一索引防重复落库，管理员处理时通过数据库行锁阻止同一记录被并发处理。检测不会阻止新文件先被检索，须由管理员完成处理才移除失效文档。
